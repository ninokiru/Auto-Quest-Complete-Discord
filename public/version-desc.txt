## 🎮 Auto Quest Complete Discord

Auto-complete Discord **video, stream and game quests** from one window. Tauri 2 + Rust behind the scenes, Vue 3 on the surface, and no cloud service in between: everything runs on your machine.

## v0.0.5 L1#2 — a patch on 0.0.5

Everything that shipped in 0.0.5 and in L1#1 is still here; this is the next set of fixes on top of it — mostly around the CDP launcher, plus one change to how game quests are queued.

### New

- **Game quests take turns on the same account.** Discord allows one game session per account, so a second game quest on an account that is already running one now waits in the queue instead of failing. Video and stream quests are unaffected, and two different accounts still run their game quests side by side.

### Fixed

- **Discord could stay closed after a failed launch.** When the debug instance never came up, the launcher now closes it and reopens Discord in normal mode instead of leaving you without Discord at all. A client that is still starting up also gets a few seconds before its port is called "occupied", which is what produced the false "port is in use" error right after a restart.
- **The connection panel used to show names.** Snowflake ids, invite codes, channel names and conversation titles are masked now, while the account-neutral routes (`/channels/@me`, `/app`) and plain labels such as "Quests" stay readable — so a report is still worth reading.
- **A detected account no longer handed its token to the interface.** Signing in with an account found on this machine now happens by id inside the backend, so the raw token never crosses the IPC boundary and never reaches the logs.
- **A symlinked Discord install was invisible.** Comparing the running client with the installed one resolves symlinks on Linux and macOS too, so the app recognises the client that is actually open.
- **Flatpak and Snap were mistaken for Vesktop.** A `.desktop` entry only counts as Vesktop when it names Vesktop itself, so a Flatpak launcher no longer gets the debugging flag handed to it.
- **Navigating Discord could interrupt a running quest.** An Activity quest holds an exclusive lock, and navigating the app is now refused while one is running instead of pulling the page out from under it.
- **Switching accounts could leave a task running for the previous one.** The account is read after the lock is taken, so a quest can no longer keep heartbeating under an account you already left.

### Checks

- The Rust suite gained tests for the launcher's restore path, for the diagnostics masking and for the game-quest slot; the frontend gained a store test that pins the queue behaviour.
- CI now also runs clippy on Windows — the only platform this release ships — and the Rust format check was split into a step of its own.

**Full Changelog**: https://github.com/ninokiru/Auto-Quest-Complete-Discord/compare/0.0.5-L1.1...0.0.5-L1.2

### How the in-app update works

1. The app compares its own version with the newest release of this repository.
2. Choosing **Update** downloads the `*-setup.exe` asset over HTTPS from GitHub.
3. The download's SHA-256 is compared with the digest GitHub publishes for that asset; a mismatch aborts before anything runs.
4. A small helper waits for this app to quit, runs the installer silently, and starts the new build.

Only Windows is self-updating in this release; other platforms still get the release page link. Downloads are restricted to GitHub hosts.

### Windows SmartScreen / Defender

These binaries are **not code-signed**. The app rewrites its own process identity and reads locally stored Discord credentials, which is exactly what heuristic scanners flag, so Defender may quarantine the download and SmartScreen may block the first launch. Confirm the file came from this repository, choose **More info → Run anyway**, and add the app folder to Defender's exclusions if it keeps deleting the file.

They will return in a later release. If you need one of them now, build it from source (`pnpm tauri:build`).
